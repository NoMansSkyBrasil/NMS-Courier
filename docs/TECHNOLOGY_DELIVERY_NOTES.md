# Technology delivery notes

Checkpoint: 2026-10-07. Owner of the technology domain: teaching the player
*known technologies* (the blueprints listed in the game catalogue), in three
modes requested by the project owner — one, several, all — and the permanent
list of entries that must never be taught.

Status in one line: the rules, the classification, the native routine and the
research profile request are **implemented and checked offline; no technology
has been taught in a running game yet.**

## What "technology" means here

The game table `METADATA/REALITY/TABLES/NMS_REALITY_GCTECHNOLOGYTABLE.MBIN`
has 393 entries in the corpus build. Teaching one adds its ID to the player's
known-technology list, which lets the player build it. It does not install
anything in an inventory and gives no module item; those are different
operations (`GcRewardInstallTech`, procedural upgrade products).

Not every entry is a technology a player can learn. Many are internal:
damaged slots of crashed ships, the parts of machines and containers, and the
templates behind procedural upgrade modules. A tool that "adds everything"
puts all of them in the player's catalogue.

#### Portal glyph entries are not the glyphs a player learns

Checked because a mistake here would matter:

- `MAINT_PORTAL1`-`16` are the sixteen chargeable carvings of a portal. They
  are installed in the portal's own button entity
  (`MODELS/PLANETS/BIOMES/COMMON/BUILDINGS/PORTAL/PORTAL/ENTITIES/BUTTON.ENTITY.MBIN`,
  as `PreInstalledTech` of its maintenance component) and listed in the
  maintenance group `Runes`. Each is chargeable with a substance type. No
  reward references them.
- The glyphs a player *knows* are a different thing: the reward type
  `GcRewardDiscoverRune` (40 uses in the reward table; one field, `AllRunes`)
  and a player-state field named `KnownPortalRunes` in the executable's
  metadata. Neither involves a technology ID.

So blocking the `MAINT_PORTAL` entries from technology delivery removes
nothing a player would want, and teaching them would not give glyphs.
Delivering portal glyphs is a separate, future operation through the
discover-rune route; it has not been investigated beyond these two facts.

### Why this holds after a game update

Three layers, each enough to refuse on its own:

1. **Structural rules** read the entry's own fields. A damaged slot, a
   maintenance part or a template added by a later version is refused by what
   it is, with no list to update.
2. **Permanent ID rules** refuse the families and names reviewed today
   whatever a later table says about them: prefixes `MAINT_`, `EXOPOD_TECH`,
   `SHIPSLOT_DMG`, `SHIPEASY_DMG`, `WEAPSLOT_DMG`, `WEAPSENT_DMG`,
   `WEAPEASY_DMG`; any ID containing `_DMG`, `DAMAGE`, `BROKEN` or `OBSOLETE`;
   and the exact name `SPIDERBRAIN`.
3. **Unreadable means refused**: a missing field, a flag that is not 0 or 1,
   an out-of-range category or an ID that does not match is never sent.

The rules exist in three places that must stay identical:

- runtime, on the running game's own definitions:
  `runtime/native/asi/technology_learn_180836.h`
  (fixture `tests/run-technology-guard-fixture.ps1`);
- application: `packages/catalog/src/technology-delivery-policy.ts`
  (tests in `packages/catalog/tests/technology-delivery-policy.test.ts`);
- research table generator: `runtime/research/classify-technology-delivery.py`
  .

A new game build still needs the addresses below revalidated before anything
is sent; the rules decide *what* may be taught, not whether the build is
supported.

### What the game itself refuses

The learn routine returns without adding when the ID is `OBSOLETE`, when
`Procedural` or `RepairTech` is set, or when the technology is already known.
It does **not** refuse damaged-slot or maintenance entries, which is why they
need our rules.

## How the game teaches a technology (offline finding)

The shipped reward type `GcRewardSpecificTech` (`TechId`, `AutoPin`,
`Silent`; 184 uses in the reward table) is how missions and the Anomaly teach
a technology. Its handler, already identified on build 180383 in
[native acquisition research](NATIVE_ACQUISITION_RESEARCH.md), does two calls:

| Routine | Build 180383 RVA | Build 180836 RVA | Arguments observed in the handler |
| --- | --- | --- | --- |
| Reward handler | `f375f0` | `f394a0` | — |
| Definition lookup | `ec6f10` | `ec8dc0` | table (`manager + 0x60`), 16-byte ID, flag `1`; returns the definition or null |
| Learn | `5a8770` | `5a95a0` | player state (`manager + 0xb940`), definition, pin flag, silent flag; returns 1 when added |

Manager pointer: RVA `6e8d708` on 180836 (the one the profile already uses).
The 180836 addresses come from a masked byte search of the 180383 routines:
each matched exactly once (70, 40 and 30 instructions).

Definition fields used, from correlating the compiled table bytes with the
converted table (entry size `0x2e0`, all 393 entries agree): ID `+0x108`,
category `+0x194` (`Maintenance` = 7), `BrokenSlotTech` `+0x2c4`, `IsTemplate`
`+0x2c9`, `Procedural` `+0x2cc`, `RepairTech` `+0x2cd`, `Teach` `+0x2ce`,
`WikiEnabled` `+0x2d1`. The learn routine reads `+0x108`, `+0x2cc`, `+0x2cd`
and `+0x2d1` at the same offsets, which ties the file layout to memory for
those fields. The known list is a vector at player state `+0x18738` with its
count at `+0x18734`.

Only 54 technologies have a shipped reward that teaches exactly that one
technology, so dispatching shipped rewards cannot cover the catalogue; the
profile calls the two routines directly instead. This is a **native call**:
nothing is written to game memory by the profile.

Not verified: the call from our update hook instead of the reward handler
(same game thread, but untested), behaviour in a menu or before a save is
loaded, the meaning of the lookup's third argument beyond "the handler passes
1", and that the in-memory offsets of `BrokenSlotTech`, `IsTemplate`, `Teach`
and the category match the file (the profile checks ID, category range and
0/1 flags and refuses otherwise).

## The request (research profile, build 180836)

- Event `technology`; request file
  `%LOCALAPPDATA%/NMSCourier/diagnostics/native-technology-request-180836-<PID>.txt`
  with optional `silent=1` and one `id=<ID>` per line, at most 256; anything
  else rejects the whole request.
- On the game's update thread, for each ID: permanent ID rules, lookup,
  structural rules on the returned definition, then the learn routine with
  pin 0. Result file `native-technology-result-180836-<PID>.txt`: known count
  before and after and one line per ID (`learned`, `not_added`, `unknown_id`
  or the blocking reason).
- Script: `runtime/native/asi/signal/signal-technology-180836.ps1` with
  `-Id A[,B...]` (one or several) or `-All` (every `deliverable` row of the
  classification table), `-ShowAlert` to let the game show its own
  new-technology alert. The script refuses blocked or unknown IDs before
  writing the request.

The three modes of the product map to these: one = `-Id X`, several =
`-Id X,Y,Z`, all = `-All`. The application-side selection function is
`selectTechnologiesForDelivery`.
