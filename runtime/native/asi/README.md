# Native startup bridge probe

The current probe is a read-only x64 `XINPUT9_1_0.dll` proxy in `Binaries`. `xinput_proxy.c` exports the four functions and ordinals of the system DLL and forwards calls to the copy loaded by absolute path from System32. On the first exported XInput call, it starts `startup_probe.c` on a worker. `DllMain` performs no file I/O, game call, hook installation, or thread creation. The worker hashes the running executable and writes `%LOCALAPPDATA%\NMSCourier\diagnostics\asi-startup-<PID>.log`. It accepts only the inspected Steam build 179666 executable SHA-256 `b7913f268dfc62386b6b68f524bfc8ade4a44a9f4fbad39085b7bf51be3680cb`; all other builds produce a rejection diagnostic. The probe never grants an item or mutates the game.

The development build used verified llvm-mingw 20260922 / LLVM 23.1.2 (archive SHA-256 `e3ad77d117a4bea19a7a3b333341824d79a5a371004a10e25b8504e7b3047666`). From this directory, compile with `x86_64-w64-mingw32-clang -std=c11 -O2 -Wall -Wextra -Werror -DCOURIER_XINPUT_PROXY_BUILD -shared -o xinput9_1_0.dll startup_probe.c xinput_proxy.c xinput_proxy.def -lbcrypt`. End users do not install a compiler. The local build SHA-256 is `713f70f35f147fdc97bd275904b75cadd570c7bfde790c251fb2194c0d6186b7`.

Static inspection of this `NMS.exe` found imports of `XInputGetState` and `XInputSetState` from `XINPUT9_1_0.dll`; the installed game had no adjacent DLL with that name, and this Windows installation had no KnownDLL entry for it. The real System32 DLL exports four functions at ordinals 2–5, matching `xinput_proxy.def`. An isolated fake `NMS.exe` loaded both the custom proxy and the original System32 XInput DLL, returned the same no-controller status (`1167`) as the baseline, and rejected the fake executable hash. Ten consecutive follow-up fixture runs exited normally with both modules present. One earlier run reported no modules from Toolhelp32 and exited with the fixture's own assertion code 4; it did not crash. This result remains unexplained and prevents claiming exhaustive startup reliability.

While the game was closed, the previous exact-hash-matched experimental proxy was replaced at `E:\SteamLibrary\steamapps\common\No Man's Sky\Binaries\xinput9_1_0.dll`. The installed hash matches `713f70f35f147fdc97bd275904b75cadd570c7bfde790c251fb2194c0d6186b7`. This is a development-only installation, not an installer or packaged feature. A first Steam launch on 2026-09-23 created `%LOCALAPPDATA%\NMSCourier\diagnostics\asi-startup-10972.log` with `status=exact_build_startup_observed`, PID 10972, and the matching NMS.exe SHA-256. The process was responsive at the first check. Loaded-save gameplay, sustained stability, clean shutdown, and controller behavior remain unverified. Before any live mutation, require those checks, a verified read-only callback across gameplay transitions, and exact in-memory build checks. If the game fails startup, close it and remove only this exact-hash-matched DLL; never delete an unexpected or third-party file.

The prior [Ultimate ASI Loader v9.7.4](https://github.com/ThirteenAG/Ultimate-ASI-Loader/releases/tag/v9.7.4) WinHTTP experiment remains in source as an inactive alternative. Its reviewed archive SHA-256 was `e5860e7d9a1805267535b65749575b5e406cc6ea3325c7392189c578815045d1`; the x64 DLL SHA-256 was `031a3e5576d91dce1e438d36b9a3d462c7334ab4791990a8ff1e3ddc0e132daf`. A fake executable crashed with `0xc0000005` under the loader's default lazy initialization. `dontloadfromdllmain=0` passed five fixture runs but was not accepted as a live-game safety proof. The loader, its config, and its `.asi` plugin were removed from the game before launch. The EXML Carbon planter patch was also removed from `GAMEDATA\MODS`; that folder is empty.

## Next read-only callback probe

`native_callback_probe.c` uses the unmodified [MinHook v1.3.4](https://github.com/TsudaKageyu/minhook/releases/tag/v1.3.4) source pinned at commit `c3fcafdc10146beb5919319d0683e44e3c30d537` under `runtime/native/vendor/minhook`, with its original license notice. The callback build adds `-DCOURIER_NATIVE_CALLBACK_PROBE` and links `buffer.c`, `hook.c`, `trampoline.c`, and `hde64.c` from that directory. It is gated behind the executable SHA-256 check and an exact 16-byte in-memory prologue at `cGcApplication.Update` RVA `0x2D7500`. The hook only increments an atomic counter, records the callback thread ID, and calls the original function. A separate worker writes `%LOCALAPPDATA%\NMSCourier\diagnostics\native-hook-<PID>.log` every two seconds, then disables the hook after 180 seconds. There is no item insertion, command transport, or save access in this build.

The production-mode callback DLL was compiled with `-Wall -Wextra -Werror`; SHA-256 is `66d5390bf51128d38fb6fdd846af2e663b4632fd641373a35c8c7b4df60ca976`. An isolated `callback_fixture.c` host using a fixture-only build observed 390 hooked callbacks while all 400 original calls completed (`hook_status=0`, process exit 0). The same fake `NMS.exe` with the production-mode DLL returned `unsupported_build`, produced no new hook log, and exited 0. The fixture-only macro `COURIER_NATIVE_CALLBACK_FIXTURE` must never be used for a game deployment. After NMS PID 1936 closed, the startup-only DLL was replaced under exact source, existing-file, and executable hash checks. The installed callback DLL hash matched `66d5390bf51128d38fb6fdd846af2e663b4632fd641373a35c8c7b4df60ca976` while the game was closed.

The live Steam process PID 28888 produced `native-hook-28888.log` with 7,319 callbacks, one callback thread ID, `hook_status=0`, and `status=observation_complete` after the 180-second window. The game remained responsive inside the loaded save. This establishes a working read-only native callback for the exact build, not a delivery result.

## Read-only inventory and one-shot Carbon test

`inventory_snapshot_179666.c` reads the personal inventory layout already checked against this executable and a prior live process. It bounds the vector, validates memory ranges, and sums `FUEL1` Carbon stacks. Its synthetic-layout fixture passes valid-quantity, malformed-vector, Carbon-template, confirmed-add, and unknown-outcome cases. The next `DeliveryTest` build combines the read-only snapshot with a one-shot native insertion path. It checks the exact 32-byte in-memory prologue of `cGcInventoryStore.Add` at RVA `0x4CE130`, copies an existing Carbon element as a template, requests exactly 500 units, and compares the live quantity before and after. The result is unknown if a native call may have happened without a verified delta; such a result must never be automatically retried.

The test trigger is a random, process-specific Windows event listed in `native-hook-<PID>.log`. It is created only by the `DeliveryTest` build and accepted once, only while a valid Carbon inventory snapshot exists. [signal-carbon-test.ps1](signal-carbon-test.ps1) checks the exact executable, installed DLL hash, callback, snapshot, and unused one-shot state before signaling it. This is a narrow local experiment, not the product's authenticated Named Pipe transport. The script reports only that the trigger was sent; delivery requires a subsequent `delivery_state=3` with an exact +500 quantity and in-game confirmation. States 4 and 5 mean unknown and rejected, respectively.

The final `DeliveryTest` DLL SHA-256 is `7a1fc34d82a91c4fca5028a18d318e776581c518c92b8935e062a5916210f3bc`. A fixture-only build proved that a signal with no inventory snapshot is rejected (`delivery_state=5`), while a fake executable using the production-mode DLL produced `unsupported_build`, no hook log, and exit 0. The signal script also rejected the preceding read-only callback DLL by hash. After PID 28888 closed, the test DLL was installed under exact source, existing-file, and executable hash checks. Steam PID 10892 then reported a valid personal inventory snapshot with one Carbon stack and total 15. One manual trigger produced `delivery_state=3`, `delivery_before=15`, `delivery_after=515`, two Carbon stacks, and the game remained responsive. A second invocation of the signal script was rejected by the one-shot state guard. The user saw the extra 500-unit stack and confirmed 515 after a normal save reload. The user manually merged the two stacks; the bridge did not emit the native item collection notification.

## Currency reward experiment

The `CurrencyTest` build adds three one-shot events and calls the exact-build `cGcRewardManager.GiveGenericReward` candidate at RVA `0xF0BD70` with `COURIER_UNITS`, `COURIER_NANITE`, or `COURIER_QS`. A separate sparse EXML patch defines each ID as a `GcRewardMoney` entry for 1,000,000,000 Units, Nanites, or Specials (Quicksilver). The prototype is installed in the local test game, and the patch appears enabled in `GCMODSETTINGS.MXML`. Its isolated argument fixture and `-Wall -Wextra -Werror` build pass. Event state `2` means only that the native call was dispatched; it must never be reported as delivery success or automatically retried. Inspect the in-game balance after each test before proceeding to another currency.

On 2026-09-23, Steam build 179666 (`NMS.exe` SHA-256 `b7913f268dfc62386b6b68f524bfc8ade4a44a9f4fbad39085b7bf51be3680cb`) loaded the currency test DLL (SHA-256 `f20d9b41344fc7460471979f56598108ed8f750327a202b879a0716d651a441d`) in PID 25244. The mod was listed as enabled, the update hook reached over 11,000 callbacks, and the personal inventory was ready. The user reported a starting Units balance of 10,460. A single `COURIER_UNITS` event was dispatched; the user then reported 1,000,010,460 Units and the game's native right-side reward notification. The user also reported a starting Nanites balance of 588, then confirmed the separate `COURIER_NANITE` call worked and showed the notification. These are live observations for local Units and Nanites grants and their native notifications. The 600-second test window expired before the Quicksilver signal, so no Quicksilver call was dispatched. Save/reload persistence for either currency, Quicksilver, repeatability, and network-player delivery remain unverified. Neither dispatched event was retried.
